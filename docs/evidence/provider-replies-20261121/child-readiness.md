## Method-independent ownership correction prepared for integration

The initial audited source had an ownership-order defect, independently of any provider choice:

- `_own_locked` fetches by authorization UUID, then locks/checks the referenced household, and only afterward compares `guardian_id` with the requesting member.
- `withdraw` similarly checks foreign child/guardian state before rejecting an unrelated actor.
- `privacy_job` checks the referenced guardian state before the ownership comparison.

For a known foreign authorization UUID, an active foreign household can produce a different rejection from an inactive foreign household. This can disclose an account-state distinction and unnecessarily lock unrelated users. This is **not a current production exposure claim**: the routes are disabled. It is a concrete source correction suitable before activation, rather than a reason to invent a verification provider or country rule.

**Implemented local change, following root approval:** owner-scope the initial public-member lookup (`id + guardian_id=request.user.pk`) and return a uniform not-found response before inspecting foreign state. Then lock/revalidate only the owned household and preserve all current actor, expiry, replay, policy and MFA checks. Keep privileged staff review separate; staff permission still needs validation. Server-only internal authority helpers should not be casually broadened.

**Acceptance:** actual PostgreSQL regression cases for owned valid/withdrawn/expired records; unrelated known active versus inactive child/guardian and unknown UUID all produce the same not-found response; no foreign row mutation/receipt/audit; valid ownership, claim replay, privacy job holds and same-household workflows remain unchanged. No migration, provider contract, new policy, age collection or territory change is needed. Root owns approval, implementation assignment and final release. The initial audit made no runtime edits. Root subsequently authorized the ownership correction and a target-independent reviewer precheck; this lane has not committed or deployed them.

## Concrete provider method package required before implementation

The next technical package should contain one selected method and its exact evidence:

1. Contracting entity, countries actually supported, product/account eligibility and total price/term; verified relationship/age/identity claims and their explicit limits. Infrastructure or representation replies alone do not supply these claims.
2. A field-level collection sequence: before parental permission, permission evidence, later child identity and binding, ongoing use, withdrawal and independent-capacity transition. Identify recipient roles, retention, local placement and all optional disclosures.
3. A sample signed success, denial, expired, revoked and duplicate assertion/event; public verification material and rotation rules; binding of tenant, environment, nonce, guardian, prospective subject, child account, purpose, notice and current policy. No production credentials or real identity documents belong in the repository.
4. A narrow source/migration plan for whatever typed evidence is actually needed. Never overload `evidence_sha256`, the one-time claim hash, or a payment receipt as parental proof.
5. Actual sandbox/authorized-fixture E2E for forgery, wrong subject/parent/tenant/notice/purpose, replay, late revocation, changed authority, callback retries, account recovery and privacy/delete/restore. Reuse unchanged account/retention tests; physical UAT is not a blocker.

A vendor auto-acknowledgement, placeholder policy reference, synthetic staff review or mailbox verification cannot close these acceptance facts. Until a concrete method and the applicable country arrangements are established, preserve the disabled production policy and truthful public-qualification boundary.

## Actual scoped correction validation

The root-authorized source patch is limited to `accounts/guardian.py` and new `accounts/test_guardian_ownership.py`:

- `_own_row` scopes the first member lookup to the current guardian; `_own_locked`, withdrawal and privacy-job lookup use it before inspecting or locking a foreign household. Owned rows are rechecked after the normal locks.
- `_review_eligible` checks current active/verified staff, permission, MFA and bound-session state **before** target lookup, using no row locks. Existing sorted household locks and current eligibility checks still run before a review mutation, avoiding an early staff-lock ordering change.
- PostgreSQL cases cover eight member routes against unknown, foreign active, inactive-child, inactive-guardian, withdrawn and expired authorizations. They assert uniform not-found responses, no foreign household lock callbacks, no foreign changes and no new receipt/audit.
- Additional cases prove unprivileged/no-permission/no-MFA review rejects before target lookup, revoked staff is checked from current state, precheck takes no `FOR UPDATE` lock, and permission lost after precheck is rejected by the existing locked check.

**Result:** 33 focused PostgreSQL tests PASS in50.730seconds, covering five new security tests plus unchanged guardian foundation/lifecycle/concurrency tests; clean database teardown and `git diff --check` PASS. Log: `/tmp/guardian-owner-first-tests.log`. This is source/fixture acceptance, not a production-method test or new legal clearance. No migration, policy/configuration, country/age rule, provider action, book change or legacy change was made. Root owns exact-head CI, integration, deployment and live verification.
