2. **Contain the affected scope.** Preserve necessary evidence before changing it; root may use already authorized session/device revocation, credential rotation or scoped service isolation as appropriate. 3. **Establish facts.** Record affected systems/data types and approximate people/records, actual geography, event timeline, current exposure, encryption/key status, provider notice/reference and actions. Preserve sanitized relevant logs with access controls/checksums; secure raw evidence privately. Ask existing provider support only through properly authorized channels; provider notification does not automatically discharge operator obligations.
4. **Assess notifications immediately.** Do not wait for complete forensics. Use the six-hour reporting clock for applicable reportable incidents. The lead/root must identify the current official reporting method/form, authorize and submit the actual report when required; store acknowledgement privately. No report is sent by adding this runbook.
5. **Check other actual duties.** Where GDPR actually applies, Article33 includes a risk-based authority-notification rule with72-hour timing; Article34 separately addresses high-risk affected-person communication. Identify actual competent authority and territorial role; do not infer a representative or fill Google's declaration fields. Other connected jurisdictions and contract notice periods require their own determination. Do not promise a worldwide72-hour rule or assume every outage is a personal-data breach.
6. **Recover and verify.** Root verifies clean release/configuration, revocations/rotation and access checks. Restoring an older snapshot requires [hold/deletion reapplication before reopening](POST_RESTORE_PRIVACY_RECONCILIATION.md), matching private-media checks and unresolved-obligation review. Disaster loss of the current instruction set remains an explicit limitation. Do not reopen writes on an unqualified restore target.
7. **Close and learn.** Record cause, containment/recovery checks, notification/no-notification reasons, remaining risks, responsible follow-up and next review. Release evidence uses aggregate references only. Review whether a targeted hold is needed; age alone never releases it. A successful tabletop is process evidence, not production failover or comprehensive legal clearance.
